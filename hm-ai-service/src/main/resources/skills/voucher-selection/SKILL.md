# 同店选券与条件检查

目标是给出有依据的候选和条件缺口，不能承诺可以核销或购买成功。

若服务端已给出校验后的任务、有效约束和本轮执行结果，沿用这些事实，不重复查店或查券。前轮条件仅在服务端明确标为已确认且仍适用时沿用；新店、新任务或未解决的歧义不能靠聊天历史补齐。

1. 确定唯一店铺。明确新店名时直接query_shop_vouchers(shopName=新店名)，参数只填真实店名，去掉“比较、查询”等请求动词；店名本身含这些字时保留。代词沿用服务端已确认ID。同名或没有店名先澄清；不任选一家。
2. 查询本轮券列表。没有券就如实说明；只比较工具展示的最多5张券，不宣称全店最优。
3. 对有希望的券批量调用inspect_voucher_conditions(voucherIds=[...])读取完整商家规则。列表中的80字规则摘要不足以确认适用性。可把本次展示的所有ID放入一次检查，避免逐券耗尽预算。
4. 区分买券预算和用餐预算。只有明确的买券预算才约束支付金额；不能拿人均消费或抵扣金额直接推算实际餐费。已售罄、未开始、已结束、未知库存或未知价格的券不选作候选。多张券叠加、找零、人数或周末可用性都必须有规则依据。
5. 对本次展示的每张券给一个check：MATCH表示原文支持用户明确提出的使用条件，CONFLICT表示存在冲突，UNKNOWN表示规则缺失、不完整或无法判断。MATCH/CONFLICT须同时引用完整规则中的连续原文ruleQuote和实际使用条件userQuote；后者仅取本轮消息或服务端保留的已确认前轮原文，不能只引预算、查询要求或库存要求。服务端给出的purchaseCheck/budgetCheck单独处理金额与库存；不能据此把周六可用改判为冲突或未知。没有使用条件依据就UNKNOWN，不把“未写限制”当作无限制。
6. 遵守服务端已校验的选择目标与unknownPolicy。默认支付最少，HIGHEST_DEDUCTION比较抵扣金额；同额按支付更少、再按券ID稳定排序。candidateVoucherId仅为提议，允许null，最终由代码在本轮已检查完整规则、库存和预算的券中选择，不得省略checks。CONFLICT永不参与；EXCLUDE排除UNKNOWN，ALLOW_PENDING允许其作为待确认候选。DEFAULT保持原策略：有明确星期时只选MATCH，其他使用条件允许待确认UNKNOWN。没有使用条件时不凭预算或偏好自动推荐；未支持或相互矛盾的偏好先澄清。模型MATCH仍是文字解释，所有候选都不保证适用、可购买或可核销。

单独选券按系统SELECTION结构输出，answer留空，sourceIds为空。checks覆盖本轮列表的每张券；完整规则为空时用UNKNOWN。不要输出自由文本推荐理由、改写金额或把Skill当作规则来源。需要平台FAQ的混合任务用MIXED，同时保留selection和实际选用的sourceIds；笔记等本轮事实由服务端保留。不能用选券结果代替其他部分，缺失的任务结果不能声称已完成。

### 交易域星期核对

有明确使用星期时，以本轮交易摘要的weekdayCheck为准。只有已确认政策且原规则指纹一致才有MATCH或CONFLICT；DRAFT、缺失或规则已变更均为UNKNOWN。禁止从自由文本再补成已确认结论。
星期政策只覆盖周几；人数、叠加等其他条件仍须单独确认。日期候选同样由代码结合预算、查询时库存和unknownPolicy，在本次展示范围按确认目标选择；额外条件不会因星期MATCH而获得确认。只有用户明确允许待确认候选时，星期或其他条件UNKNOWN才可参与，仍不保证适用。模型不能改变代码排序结果。
